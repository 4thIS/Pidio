# Pidio 기술 설명서

> 라즈베리파이 5 기반 학교 미디어 플레이어 — 아키텍처·설계 결정·구현 근거
>
> 이 문서는 **"왜 이렇게 만들었는가"**에 답하기 위해 작성되었다. 각 항목은 실제 소스 파일을 근거로 하며, 파일 경로를 함께 표기했다.

## 0. 한 문단 요약

Pidio는 **라즈베리파이 5를 학교 TV에 HDMI로 연결해두고, 교직원이 같은 랜(LAN) 안의 PC·스마트폰 브라우저에서 재생을 관리하는 미디어 플레이어**다. USB에 담긴 동영상·사진·음악을 자동 인식하고, 사진 슬라이드쇼에 배경음악을 얹은 "블록" 단위로 재생 목록을 구성하며, 요일·시간대 예약으로 무인 자동 재생을 수행한다. 백엔드는 Python 3.11 + FastAPI + SQLite, 재생은 **mpv 2개 인스턴스를 JSON IPC로 원격 제어**, 프론트는 Vue 3 SPA다. 테스트는 백엔드 185개(pytest), 프론트 33개(vitest)가 통과한다.

## 1. 문제 정의와 요구사항

### 1.1 해결하려는 문제
학교에서 TV·모니터에 안내 영상, 행사 사진, 배경음악을 상시 재생하려면 보통 다음 중 하나를 쓴다.

| 기존 방식 | 한계 |
|---|---|
| PC를 상시 켜둠 | 전력·소음·비용, 화면보호기·업데이트 팝업 |
| USB 직결 TV 내장 플레이어 | 재생목록 구성 불가, 예약 불가, 사진+음악 동시 재생 불가 |
| 상용 디지털 사이니지 | 비용, 인터넷 의존, 콘텐츠 등록 절차 복잡 |

Pidio는 **저전력 상시 구동 + 원격 관리 + 오프라인 동작**을 동시에 만족시키는 것이 목표다.

### 1.2 기능 요구사항
- USB 미디어 자동 인식(동영상/사진/음악)
- 사진 슬라이드쇼 + 배경음악 동시 재생
- 재생목록(플레이리스트) 구성·저장·편집
- 요일/시간대 및 날짜구간 예약 자동 재생
- 웹 브라우저 기반 원격 제어(별도 앱 설치 불필요)
- 재생 상태 실시간 표시(현재 곡, 진행바)

### 1.3 비기능 요구사항
- **오프라인 동작**: 학교 내부망만으로 동작(외부 인터넷·클라우드 불필요)
- **무인 복구**: 정전 후 재부팅되면 자동으로 이전 예약 상태 복귀
- **하드웨어 없는 개발**: 개발자 PC(Windows)에서 mpv·USB 없이 로직 테스트 가능

## 3. 핵심 설계 결정 (Design Decisions)

교수님 질문이 집중될 만한 지점을 "왜 그렇게 했는가" 중심으로 정리한다.

### 3.1 왜 mpv를 2개 인스턴스로 띄우는가?

**문제:** "사진 슬라이드쇼를 넘기면서 그 위에 배경음악을 계속 재생"해야 한다. 하나의 플레이어 인스턴스로는 사진을 교체할 때마다 오디오도 함께 끊긴다.

**결정:** 역할이 다른 mpv 프로세스를 2개 띄운다.
- **화면 채널(video)**: 동영상 또는 사진 이미지를 표시. 사진이 넘어갈 때마다 `loadfile`로 교체된다.
- **음악 채널(music)**: 배경음악만 담당. 사진이 몇 장 넘어가든 **끊기지 않는다.**

```python
# backend/app/domain/player.py — _load_current()
if b.kind == "video":
    self.m.stop()                                    # 동영상은 자체 소리 → 음악 채널 정지
    extra = {"loop-file": "inf"} if self.repeat == "one" else None
    self.v.loadfile(self._resolve(b.video_id), extra)
else:  # slideshow
    if b.music_id:
        self.m.loadfile(self._resolve(b.music_id), {"loop-file": "inf"})
    else:
        self.m.stop()
    if b.photos:
        pid, sec = b.photos[0]
        self.v.loadfile(self._resolve(pid), {"image-display-duration": sec})
```

**대안과 기각 사유:**

| 대안 | 기각 사유 |
|---|---|
| VLC / 자체 플레이어 구현 | RPi의 하드웨어 디코더(H.264/HEVC) 활용과 DRM 직접 출력에서 mpv가 가장 안정적. 자체 구현은 코덱 대응 비용이 과다 |
| mpv 1개 + 오디오 필터 | 이미지 교체 시 오디오 파이프라인이 리셋되어 끊김 발생 |
| 데스크톱 환경(X11) 위에서 실행 | Lite(무GUI) 대비 메모리·부팅시간 손해. DRM 직접 출력이 더 가볍고 안정적 |

### 3.2 왜 mpv를 JSON IPC로 제어하는가?

**결정:** mpv를 `--input-ipc-server=<socket>` 옵션으로 상주시키고, 백엔드가 **유닉스 도메인 소켓에 JSON 한 줄씩** 명령을 보낸다.

```python
# backend/app/domain/mpv_ipc.py
def encode_command(args: list, request_id=None) -> str:
    obj = {"command": args}
    if request_id is not None:
        obj["request_id"] = request_id
    return json.dumps(obj) + "\n"
```

**이 방식의 이점:**
1. **프로세스 분리**: 웹 서버가 재시작돼도 mpv는 살아 있다(재생 끊김 없음). 반대로 mpv가 죽어도 웹 UI는 응답한다.
2. **재연결 자동화**: mpv가 재기동되면 감시 스레드가 소켓을 다시 연다.
   ```python
   def _monitor(self) -> None:
       while not self._stop:
           if self._sock is None:
               self._open()   # mpv 재기동 시 소켓 복구
           time.sleep(2)
   ```
3. **양방향 통신**: 명령 전송뿐 아니라, mpv가 보내는 `end-file` 이벤트를 받아 "다음 사진/다음 블록"으로 진행한다. 폴링이 필요 없다.

**동시성 처리:** 웹 요청이 동시에 들어와도 소켓 쓰기가 섞이지 않도록 `threading.Lock`으로 보호한다. 값을 읽는 `get_property`(진행바용 `time-pos`)는 **`request_id`로 요청·응답을 상관(correlate)** 시켜 다른 응답과 섞이지 않게 했다.

```python
def get_property(self, name, timeout: float = 1.0):
    rid = next(self._ids)
    ev = threading.Event()
    self._pending[rid] = [ev, None]
    ...
    ok = ev.wait(timeout)        # 응답 대기(타임아웃 있음 → 무한 블로킹 방지)
    slot = self._pending.pop(rid, None)
    return slot[1] if (ok and slot) else None
```

### 3.3 왜 파일을 경로가 아니라 `content_id`로 식별하는가?

**문제:** USB 안의 파일은 사용자가 이름을 바꾸거나 폴더를 옮길 수 있다. 경로를 키로 쓰면 그 순간 플레이리스트가 깨진다.

**결정:** 파일 **내용 기반 부분 해시**를 식별자로 쓴다.

```python
# backend/app/domain/identity.py
def compute_content_id(path: str) -> str:
    size = os.path.getsize(path)
    with open(path, "rb") as f:
        if size <= 2 * _CHUNK:          # 2MB 이하 → 전체 해시
            head = f.read(); tail = b""
        else:                            # 큰 파일 → 앞 1MB + 뒤 1MB
            head = f.read(_CHUNK)
            f.seek(-_CHUNK, os.SEEK_END)
            tail = f.read(_CHUNK)
    h1 = hashlib.sha1(head).hexdigest()[:16]
    h2 = hashlib.sha1(tail).hexdigest()[:16]
    return f"{size}-{h1}-{h2}"           # 예: "9568-ed6b558060626db4-da39a3..."
```

**"왜 전체 파일을 해시하지 않는가?"**
4K 동영상은 수 GB다. 전체 SHA-1은 USB 읽기 속도에 묶여 수십 초가 걸리고, 파일이 수백 개면 스캔이 사실상 불가능해진다. **크기 + 앞 1MB + 뒤 1MB** 조합은 다음을 만족한다.
- 읽기량이 파일 크기와 무관하게 상수(최대 2MB) → 스캔이 빠르다
- 크기가 다르면 즉시 다른 id → 충돌 가능성이 매우 낮다
- 동영상 컨테이너는 앞(헤더)과 뒤(인덱스/moov)가 파일마다 다르므로 판별력이 높다

**"충돌하면 어떻게 되는가?"**
크기가 정확히 같고 + 앞 1MB가 같고 + 뒤 1MB도 같아야 충돌한다. 학교에서 다루는 미디어 파일 규모에서는 사실상 발생하지 않으며, 충돌 시에도 "두 파일이 하나로 인식"될 뿐 데이터 손실은 없다. 암호학적 무결성 검증이 목적이 아니라 **동일 파일 재인식**이 목적이므로 이 트레이드오프는 타당하다.

### 3.4 왜 "블록(Block)"이라는 재생 단위를 도입했는가?

**문제:** "사진 5장에 노래 1곡을 깔고, 그 다음 동영상 1개를 재생"하는 구조를 어떻게 표현할 것인가? 단순한 "파일의 리스트"로는 사진과 음악의 **동시성**을 표현할 수 없다.

**결정:** 재생의 최소 단위를 파일이 아니라 **블록**으로 정의했다.

```python
# backend/app/domain/contracts.py
@dataclass
class Block:
    """재생 단위. kind='video'는 동영상 1개, kind='slideshow'는 사진들+선택 음악."""
    kind: Literal["video", "slideshow"]
    video_id: Optional[str] = None                                # kind='video'
    music_id: Optional[str] = None                                # 배경음악(None=무음)
    photos: list[tuple[str, float]] = field(default_factory=list) # (photo_id, 표시초)
```

| 블록 종류 | 화면 | 소리 |
|---|---|---|
| `video` | 동영상 | 동영상 자체 음성 |
| `slideshow` (사진 有, 음악 有) | 사진 순차 표시 | 배경음악 반복 |
| `slideshow` (사진 有, 음악 無) | 사진 순차 표시 | 무음 |
| `slideshow` (사진 無, 음악 有) | "음악 재생 중" 안내 화면 | 음악 |

이 모델의 장점은 **"음악 1곡이 사진 N장에 걸친다"는 관계가 데이터 구조 자체로 표현**된다는 점이다. 사진당 표시 시간은 `photos` 튜플의 두 번째 값으로 개별 지정되며, UI에서는 "노래 길이 ÷ 사진 수"로 자동 계산해 보여준다.

**DB 스키마도 이 모델을 그대로 반영한다:**
```sql
CREATE TABLE playlist_blocks (
  id INTEGER PRIMARY KEY,
  playlist_id INTEGER REFERENCES playlists(id) ON DELETE CASCADE,
  position INTEGER,                                  -- 블록 순서
  kind TEXT NOT NULL,                                -- 'video' | 'slideshow'
  video_id TEXT REFERENCES media(content_id),
  music_id TEXT REFERENCES media(content_id)         -- NULL = 무음
);
CREATE TABLE block_photos (
  block_id INTEGER REFERENCES playlist_blocks(id) ON DELETE CASCADE,
  position INTEGER, photo_id TEXT, duration_sec REAL,
  PRIMARY KEY (block_id, position)
);
```

### 3.5 왜 재생 큐를 백엔드가 소유하는가?

**결정:** mpv에는 **현재 재생할 파일 하나만** `loadfile`로 넘긴다. 큐 전체(순서·반복·셔플)는 백엔드 `Player`가 관리한다.

**이유:**
1. mpv의 내장 플레이리스트 기능은 "사진+음악 동시" 같은 블록 개념을 표현할 수 없다.
2. 재생 중 큐를 편집(추가/삭제/순서변경)해도, 백엔드가 소유하고 있으면 **현재 재생 중인 항목을 유지**한 채 재계산할 수 있다.

**"재생 중에 큐를 편집하면 현재 곡이 바뀌지 않는가?"** — 이 문제를 객체 정체성(identity) 추적으로 해결했다.

```python
# backend/app/domain/player.py
def _index_in_queue(self, block):
    """block 객체의 큐 내 인덱스(정체성 비교). 없으면 None."""
    for i, b in enumerate(self.queue):
        if b is block:            # 값(==)이 아니라 정체성(is) 비교
            return i
    return None

def _restore_pos(self, block):
    """큐/순서 변경 후, 재생 중이던 block 을 계속 가리키도록 pos 재계산."""
    qi = self._index_in_queue(block)
    self.pos = self.order.index(qi) if qi is not None else -1
```

`enqueue`, `remove`, `reorder`, `set_shuffle` 모두 "① 현재 블록 객체를 붙잡아두고 → ② 큐를 변경하고 → ③ 그 객체를 다시 찾아 위치 복원"하는 동일한 패턴을 따른다.

`is` 비교를 쓴 이유: 같은 내용의 블록이 큐에 여러 개 있을 수 있으므로(같은 사진을 두 번 넣는 경우), 값 비교로는 어느 것이 재생 중인지 구분할 수 없다.

### 3.6 왜 셔플을 "별도 order 배열"로 구현했는가?

```python
self.queue = []   # 원본 순서 (사용자가 편집하는 대상)
self.order = []   # 재생 순서 (셔플이 반영된 큐 인덱스 목록)
self.pos = -1     # order 상의 위치
```

큐 자체를 뒤섞으면 셔플을 껐을 때 원래 순서로 되돌릴 수 없다. **원본은 보존하고 재생 순서만 별도 배열로 관리**하면 셔플 on/off가 무손실 토글이 된다.

또한 "전체를 한 바퀴 돌면 다시 섞는" 동작(음악 스트리밍 서비스들의 일반적 방식)을 자연스럽게 구현할 수 있다.

```python
def _advance(self):
    if self.repeat == "one":
        self._load_current(); return
    if self.pos + 1 < len(self.order):
        self.pos += 1; self._load_current(); return
    if self.repeat == "all":
        if self.shuffle:
            self._rebuild_order()   # 한 바퀴 다 돌면 새로 셔플
        self.pos = 0; self._load_current()
    else:
        self.pos = -1; self._to_standby()
```

### 3.7 왜 SSE(Server-Sent Events)를 썼는가? WebSocket이 아니라?

**요구:** 재생 상태(현재 곡, 진행바, 재생/일시정지)를 **여러 브라우저에 동시에** 실시간 반영해야 한다. A교사가 곡을 넘기면 B교사 화면에도 즉시 보여야 한다.

**결정:** SSE(`GET /events`, `text/event-stream`)를 선택했다.

| 비교 항목 | SSE | WebSocket | 폴링 |
|---|---|---|---|
| 통신 방향 | 서버→클라이언트 단방향 | 양방향 | 클라이언트 주도 |
| 이 프로젝트에 필요한 방향 | **일치** (제어는 일반 REST로 충분) | 과잉 | — |
| 자동 재연결 | 브라우저 내장 (`EventSource`) | 직접 구현 필요 | — |
| 프로토콜 복잡도 | 일반 HTTP | 별도 핸드셰이크·프레이밍 | 단순하나 낭비 |
| 지연/부하 | 낮음 | 낮음 | 주기만큼 지연 + 상시 요청 |

제어 명령(재생/정지/다음)은 평범한 `POST /api/player/...`로 보내고, 상태 방송만 SSE로 받는다. **양방향이 필요 없는데 WebSocket을 쓰는 것은 불필요한 복잡도**라고 판단했다.

**구현: 허브(Hub) 팬아웃**
```python
# backend/app/web/sse.py
class StateHub:
    """구독자 큐 집합으로의 상태 팬아웃."""
    def publish(self, state: PlayerState) -> None:
        """상태를 모든 구독자에게 전달. 어느 스레드에서 호출해도 안전."""
        loop = self._loop
        for q in list(self._subscribers):
            if loop is not None and loop.is_running():
                loop.call_soon_threadsafe(q.put_nowait, state)   # 다른 스레드 → 이벤트 루프
            else:
                q.put_nowait(state)
```

`call_soon_threadsafe`를 쓴 이유: 상태 변경은 **mpv 이벤트를 받는 별도 스레드**에서도 발생한다(사진 자동 전환 등). asyncio 큐는 스레드 안전하지 않으므로, 이벤트 루프에 안전하게 넘겨야 한다.

**도메인 → 웹 연결(의존 역전):** 도메인은 SSE를 모른다. 대신 콜백 훅만 노출하고, 웹 계층이 앱 조립 시점에 꽂는다.
```python
# backend/app/web/main.py
app.state.deps.player.on_state_change = (
    lambda: app.state.hub.publish(app.state.deps.player.get_state())
)
```

### 3.8 왜 진행바를 "1초 SSE + 프론트 보간"으로 만들었는가?

**문제:** 진행바를 위해 `time-pos`를 초당 60번 조회하면 IPC 왕복이 과도하다. 그렇다고 1초마다만 갱신하면 진행바가 **뚝뚝 끊겨** 보인다.

**결정:** 서버는 1초마다 정확한 값을 보내고, 브라우저는 그 사이를 `requestAnimationFrame`으로 보간한다.

```js
// frontend/src/components/NowPlaying.vue — rAF 보간
function tick() {
  if (isPlaying.value && dur.value > 0) {
    smoothPos.value = Math.min(base + (performance.now() - baseAt) / 1000, dur.value)
  } else {
    smoothPos.value = pos.value
  }
  raf = requestAnimationFrame(tick)
}
```
SSE로 새 값이 오면 `base`/`baseAt`을 리셋하므로 **오차가 누적되지 않는다**(1초마다 진실값으로 보정).

**서버 측:** `get_property`는 소켓 응답을 기다리는 블로킹 호출이므로, 이벤트 루프를 막지 않도록 executor(스레드풀)로 넘긴다.
```python
# backend/app/web/background.py
async def run_position_loop(deps, hub, interval: float = 1.0) -> None:
    """1초 주기로 진행바 갱신 방송. mpv get_property는 블로킹이라 executor로."""
    loop = asyncio.get_event_loop()
    while True:
        await asyncio.sleep(interval)
        await loop.run_in_executor(None, position_tick, deps, hub)
```

**사진의 진행바는 왜 다른가?** mpv는 정지 이미지에 대해 `time-pos`/`duration`을 제대로 주지 않는 경우가 많다. 그래서 사진일 때는 **벽시계(monotonic clock)로 경과 시간을 계산**한다.
```python
# backend/app/domain/player.py — refresh_position()
if b.photos:
    idx = min(self._photo_idx, len(b.photos) - 1)
    sec = float(b.photos[idx][1] or 0)
    started = self._photo_started if self._photo_started is not None else time.monotonic()
    self.duration_sec = sec
    self.position_sec = max(0.0, min(time.monotonic() - started, sec))
    return
```
`time.monotonic()`을 쓴 이유: 시스템 시각이 NTP로 보정되어도 뒤로 가지 않는 단조 증가 시계여야 진행바가 역행하지 않는다.

### 3.9 예약(스케줄) 로직

**요구:** "평일 오전 8시~9시엔 등교 음악", "졸업식 당일 10~12시엔 졸업 영상" 같은 두 종류의 예약이 필요하다.

**결정:** 두 타입을 정의하고 우선순위로 충돌을 해소한다.

```
우선순위: weekly (요일 반복) > date_range (날짜 구간) > 기본 재생목록
```

```python
# backend/app/domain/scheduler.py
def active_playlist_id(schedules, now: dt.datetime, default_id):
    weekly = [s for s in schedules
              if s.get("enabled", 1) and s["sched_type"] == "weekly" and _weekly_active(s, now)]
    if weekly:
        return weekly[0]["playlist_id"]
    dated = [s for s in schedules
             if s.get("enabled", 1) and s["sched_type"] == "date_range" and _date_active(s, now)]
    if dated:
        return dated[0]["playlist_id"]
    return default_id
```

**같은 타입끼리 겹치면?** 저장 시점에 거부한다(`ScheduleConflict` → HTTP 409). 실행 시점에 임의로 하나를 고르면 사용자가 예측할 수 없기 때문에, **모호성을 입력 단계에서 차단**하는 편이 낫다고 판단했다.

```python
def _ranges_overlap(a_start, a_end, b_start, b_end) -> bool:
    return a_start < b_end and b_start < a_end     # 경계는 겹침으로 보지 않음
```
종료 시각을 **배타적(exclusive)**으로 둔 이유: "8:00~9:00"과 "9:00~10:00"이 연속 예약으로 자연스럽게 이어지게 하기 위함이다.

**수동 개입과의 관계 (mode: auto / manual):**
교사가 수동으로 다른 것을 재생하면 `mode="manual"`이 되어 **예약이 화면을 뺏어가지 않는다.**
```python
# backend/app/domain/service.py — evaluate_schedule()
if self.player.mode == "manual":
    return                        # 수동 조작 중 → 스케줄 전환 안 함
```
단, 예약이 걸려 있다는 **사실 자체**는 모드와 무관하게 계속 갱신해서 UI에 "예약 재생으로 복귀" 버튼을 띄운다. 이 분리 덕분에 "수동으로 잠깐 다른 걸 틀었다가 원래 예약으로 돌아가기"가 한 번의 클릭으로 가능하다.

**평가 주기:** 1분마다 틱을 돈다(`_TICK_SECONDS = 60`). 예약 단위가 분이므로 그보다 조밀할 필요가 없다.

### 3.10 왜 ORM 없이 표준 `sqlite3`를 쓰는가?

**결정:** SQLAlchemy 등 ORM 없이 표준 라이브러리 `sqlite3`만 사용한다.

| 근거 | 설명 |
|---|---|
| 스키마 규모 | 테이블 8개, 관계 단순. ORM의 추상화 이득보다 학습·의존성 비용이 큼 |
| 성능 | RPi는 자원이 제한적. ORM 레이어와 마이그레이션 도구는 부팅·메모리 부담 |
| 투명성 | 실행되는 SQL이 코드에 그대로 보여 디버깅·최적화가 직접적 |
| 의존성 최소화 | 오프라인 설치·배포가 단순해짐(런타임 의존성 3개: fastapi, uvicorn, python-multipart) |

**동시성 처리:** SQLite는 파일 기반이므로 스레드 이슈에 주의해야 한다.
```python
# backend/app/domain/db.py
def connect(path: str) -> sqlite3.Connection:
    conn = sqlite3.connect(path, check_same_thread=False)
    conn.row_factory = sqlite3.Row          # 컬럼명 접근(row["name"])
    conn.execute("PRAGMA foreign_keys=ON")  # FK 캐스케이드 활성화(기본 꺼져 있음)
    return conn
```
- `check_same_thread=False`: FastAPI는 요청을 스레드풀에서 처리하므로 필요.
- `PRAGMA foreign_keys=ON`: SQLite는 FK를 **기본적으로 강제하지 않는다.** 이걸 켜야 플레이리스트 삭제 시 블록·사진이 `ON DELETE CASCADE`로 함께 정리된다.

**마이그레이션:** 별도 도구 없이 "재실행 안전한" 함수로 처리한다.
```python
# backend/app/domain/db.py
def _migrate(conn):
    """기존 DB에 없는 컬럼을 추가(재실행 안전). CREATE IF NOT EXISTS로는 컬럼 추가 불가."""
    def cols(table):
        return {r[1] for r in conn.execute(f"PRAGMA table_info({table})")}
    if "sort_order" not in cols("playlists"):
        conn.execute("ALTER TABLE playlists ADD COLUMN sort_order INTEGER DEFAULT 0")
```

### 3.11 "파일시스템이 진실의 원천(Source of Truth)"

**원칙:** USB 안의 실제 파일이 진실이고, DB는 **부가정보(메타데이터) 캐시**다.

스캔할 때 이번에 발견된 파일 집합만 `available=1`로 표시한다.
```python
# backend/app/domain/scanner.py
def scan_library(conn, usb_root, id_fn=compute_content_id) -> dict:
    seen: set[str] = set()
    ...
    mr.set_available(conn, seen)      # 이번 스캔에 있는 것만 available
    return {"added": added, "seen": len(seen)}
```

**이 설계의 이점:** USB를 뽑으면 목록에서 사라지고, 다시 꽂으면 **이전에 만든 플레이리스트가 그대로 되살아난다**(content_id가 같으므로). 사용자 제목 수정·표시 시간 설정 같은 부가정보도 유지된다.

## 4. 데이터 모델

### 4.1 ER 개요

```
media (content_id PK)                      ← 모든 미디어의 메타데이터
  ▲             ▲              ▲
  │             │              │
playlist_blocks │           folder_items ──► folders
  │  (video_id) │ (music_id)
  ▼
block_photos (photo_id)

playlists ──1:N──► playlist_blocks ──1:N──► block_photos
playlists ──1:1──► schedules
settings (key-value)   ← 비밀번호 해시·세션 키·기본 플리 id
```

### 4.2 주요 테이블 설계 의도

| 테이블 | 설계 의도 |
|---|---|
| `media` | `content_id`가 PK. `rel_path`는 스캔 시 갱신되는 **현재 위치**일 뿐 식별자가 아님. `available`로 USB 탈착 반영 |
| `playlist_blocks` | 재생 단위(§3.4). `position`으로 순서 유지 |
| `block_photos` | 블록 안의 사진 순서와 개별 표시 시간. PK `(block_id, position)` |
| `schedules` | 두 타입(`weekly`/`date_range`)을 한 테이블에 두고 NULL 컬럼으로 구분 |
| `folders` / `folder_items` | **태그 방식**: 한 미디어가 여러 폴더에 동시 소속 가능(물리 폴더가 아니라 논리적 묶음) |
| `settings` | key-value. 비밀번호 해시·세션 서명키·기본 플리 등 |

`folders`를 태그 방식으로 한 이유: 물리 폴더 이동은 USB 파일을 실제로 옮겨야 하고 느리며 되돌리기 어렵다. 논리적 소속으로 두면 같은 사진을 "체육대회"와 "2학기"에 동시에 넣을 수 있다.

## 5. 테스트 전략

### 5.1 "하드웨어 없이 테스트한다" — 의존성 주입

**문제:** 재생 로직을 테스트하려면 매번 라즈베리파이와 TV, USB가 필요한가? 그러면 개발 속도가 무너진다.

**결정:** 도메인 계층이 mpv를 **인터페이스(Protocol)로만** 알게 한다.

```python
# backend/app/domain/contracts.py
class MpvClient(Protocol):
    """단일 mpv 인스턴스 제어. 화면용/음악용 각각 주입."""
    def loadfile(self, path: str, extra: dict | None = None) -> None: ...
    def set_property(self, name: str, value) -> None: ...
    def command(self, *args) -> None: ...
    def stop(self) -> None: ...
    def on_end_file(self, callback) -> None: ...
    def get_property(self, name: str, timeout: float = 1.0): ...
```

`Player`는 생성자에서 이 인터페이스를 주입받는다.
```python
class Player:
    def __init__(self, video, music, standby_image, music_screen_image, ...):
        self.v = video     # 무엇이 들어오든 MpvClient 규약만 지키면 됨
        self.m = music
```

**실행 환경별 주입 대상:**

| 환경 | 주입되는 구현 | 위치 |
|---|---|---|
| 라즈베리파이(운영) | `MpvIpc` (실제 소켓) | `PIDIO_MPV=ipc` 환경변수로 선택 |
| 개발 PC(Windows) | `NullMpv` (무동작) | 기본값 |
| 단위 테스트 | `FakeMpv` (호출 기록) | `tests/fakes.py` |

# backend/app/web/deps.py
def _make_mpv_clients(testing: bool):

## 6. 웹 계층 세부

### 6.1 인증

**요구:** 학교 내부망 전용이지만 아무나 조작하면 곤란하다. 다만 교직원이 계정을 각자 만들 필요는 없다.

**결정:** **공용 비밀번호 + 서명 세션 쿠키**. 외부 인증 라이브러리 없이 표준 라이브러리로 구현했다.

```python
# backend/app/web/auth.py
_PBKDF2_ITERATIONS = 200_000

def hash_password(password: str) -> str:
    salt = os.urandom(16)
    dk = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, _PBKDF2_ITERATIONS)
    return f"pbkdf2_sha256${_PBKDF2_ITERATIONS}${salt.hex()}${dk.hex()}"

def verify_password(password: str, stored: str) -> bool:
    ...
    return hmac.compare_digest(dk.hex(), hash_hex)   # 타이밍 공격 방지
```

**보안 고려 사항:**
- 비밀번호는 평문 저장하지 않고 **PBKDF2-HMAC-SHA256 20만 회 + 임의 salt**로 해시
- 비교는 `hmac.compare_digest`로 **상수 시간** 비교(타이밍 공격 방지)
- 세션 쿠키는 **HMAC-SHA256 서명**(위조 방지), `httponly=True`(JS 접근 차단), `samesite="lax"`(CSRF 완화)
- 서명 키는 최초 생성 후 DB에 저장 → **서버 재시작해도 로그인 유지**
- 연속 5회 실패 시 429(무차별 대입 완화)

### 6.2 청크 업로드

**문제:** 4K 동영상은 수 GB다. 단일 POST로 올리면 타임아웃·메모리 문제가 발생하고, 실패 시 처음부터 다시 올려야 한다.

**결정:** 3단계 청크 업로드.
```
POST /api/upload/init                     → upload_id 발급
PUT  /api/upload/{id}/chunk?index=N  (×N) → 청크 순차 전송
POST /api/upload/{id}/complete            → 병합 → content_id 계산 → USB 타입 폴더로 이동
                                            → media 등록 → 백그라운드로 길이/썸네일 생성
```
USB가 마운트되지 않았으면 409를 반환해 사용자에게 명확히 알린다.

### 6.3 Range 스트리밍

브라우저에서 동영상을 미리보기하려면 **탐색(seek)** 이 되어야 한다. HTTP Range 요청을 지원해 206 Partial Content로 응답한다.

```python
# backend/app/web/streaming.py
headers = {
    "Content-Range": f"bytes {start}-{end}/{file_size}",
    "Accept-Ranges": "bytes",
    "Content-Length": str(length),
}
return StreamingResponse(body(), status_code=206, headers=headers, ...)
```
파일을 통째로 메모리에 올리지 않고 64KB씩 제너레이터로 흘려보내 **메모리 사용량을 상수로 유지**한다(RPi의 제한된 RAM 고려).

### 7.2 Timeline — 블록 모델의 시각화

`Timeline.vue`는 §3.4의 블록 모델을 **직접 조작 가능한 UI**로 표현한 핵심 컴포넌트다. 플레이리스트 편집 모달과 라이브 재생목록에서 **동일 컴포넌트를 공유**한다(DRY).

- 미디어를 셀로 가로 배치하고, **음악 셀을 사진 셀 위로 끌어다 놓으면** 그 사진의 배경음악이 된다 → 내부적으로 `Block(kind='slideshow', music_id=..., photos=[...])`가 만들어진다
- 노래 바의 **좌우 핸들을 끌어 여러 사진에 걸칠 수 있고**, 드래그 중 커서를 따라 부드럽게 미리보기되며 놓는 순간 사진 경계로 스냅된다
- 노래 바 자체를 잡아 다른 사진으로 옮길 수 있다
- 사진 수가 바뀌면 "노래 길이 ÷ 사진 수"로 사진당 표시 시간이 자동 재계산된다

라이브 재생목록에서의 편집은 즉시 `POST /api/player/queue/set_blocks`로 전송되어 **재생 중에도 반영**된다(§3.5의 현재 항목 유지 로직이 여기서 동작한다).

### 7.3 접근성·테마
- 다크/라이트 두 테마를 CSS 변수(`--bg`, `--text`, `--muted`, `--accent` 등)로 전환. 선택은 `localStorage`에 저장
- 라이트 테마는 흰 배경 대비를 고려해 보조 텍스트 색을 별도로 조정(WCAG 대비비 기준으로 점검)
- 재생 컨트롤(재생/일시정지/이전/다음/반복/셔플)은 이모지 대신 **인라인 SVG 아이콘**을 사용해 플랫폼별 렌더링 차이를 제거

## 8. 배포와 운영

### 8.1 systemd 3-유닛 구성

| 유닛 | 역할 |
|---|---|
| `pidio-mpv-video.service` | 화면 채널 mpv 상주 |
| `pidio-mpv-music.service` | 음악 채널 mpv 상주 |
| `pidio-web.service` | FastAPI 웹 서버 |

**기동 순서 보장:** 웹 서버는 mpv 소켓이 준비된 뒤에 떠야 한다. `After=`만으로는 "프로세스 시작"만 보장되고 "소켓 생성"은 보장되지 않으므로, 소켓 파일을 실제로 확인하는 `ExecStartPre`를 두었다.
```ini
# deploy/pidio-web.service
After=pidio-mpv-video.service pidio-mpv-music.service network-online.target
ExecStartPre=/usr/bin/bash -c 'for i in $(seq 1 30); do \
  [ -S "$PIDIO_MPV_VIDEO_SOCK" ] && [ -S "$PIDIO_MPV_MUSIC_SOCK" ] && exit 0; sleep 0.5; done; exit 1'
Restart=always
RestartSec=3
```
`Restart=always`로 예기치 못한 종료 시 자동 복구된다(무인 운영 요구사항).

### 8.2 모니터 호환성 — 해상도 자동 대응

**요구:** 학교마다 TV/모니터 해상도가 다르다. 해상도를 하드코딩하면 다른 모니터에서 깨진다.

**결정:** DRM 서브시스템에서 연결된 디스플레이를 감지해 mpv 옵션을 분기한다.
```bash
# deploy/start-mpv-video.sh
for s in /sys/class/drm/card*-*/status; do
  [ "$(cat "$s" 2>/dev/null)" = "connected" ] && DISPLAY_CONNECTED=yes && break
done

if [ "$DISPLAY_CONNECTED" = "yes" ]; then
  exec mpv "${COMMON[@]}" --force-window=yes --fs --vo=gpu --gpu-context=drm
else
  exec mpv "${COMMON[@]}" --vo=null      # 헤드리스: 화면 없이 디코드만
fi
```
- **모니터 있음**: `--vo=gpu --gpu-context=drm`으로 데스크톱 환경 없이 직접 출력. `--fs`로 연결된 디스플레이의 기본 해상도에 자동 전체화면 → 어떤 모니터든 대응
- **모니터 없음(헤드리스 개발)**: `--vo=null`로 디코드만 수행. 재생·진행바·소리는 정상 동작하므로 **모니터 없이도 원격 개발·테스트가 가능**하다

### 8.3 환경 설정

### 8.4 의존성 관리 — uv

Python 버전과 라이브러리를 **uv**로 고정한다(`pyproject.toml` + `uv.lock`). `uv sync`가 lock 파일 기준으로 가상환경을 정확히 재현하므로, 두 개발자와 라즈베리파이의 환경이 항상 동일해진다. pip를 직접 쓰지 않는 것을 규칙으로 두어 환경 불일치를 차단했다.

**런타임 의존성은 3개뿐이다**: `fastapi`, `uvicorn[standard]`, `python-multipart`. 오프라인 설치와 배포가 단순하다.

## 10. 예상 질문과 답변

### Q1. 왜 라즈베리파이인가? 미니PC나 안드로이드 TV 박스가 아니라?
- **저전력 상시 구동**(약 5~10W)으로 학교에서 24시간 켜두기에 적합
- **GPIO·HDMI-CEC 등 확장 여지**와 리눅스 표준 환경(systemd, mpv)을 그대로 쓸 수 있음
- 안드로이드 박스는 앱 배포·백그라운드 제약·자동 시작 제어가 까다롭고, 미니PC는 비용·전력이 크다
- RPi 5는 하드웨어 비디오 디코딩으로 4K 재생이 가능하다

### Q2. 인터넷이 끊기면 동작하나?
**동작한다.** 모든 미디어는 USB에 있고, 웹 UI는 라즈베리파이 자신이 서빙하며, DB도 로컬 SQLite다. 외부 서비스 의존이 전혀 없다. 학교 내부망(또는 직결 랜)만 있으면 관리가 가능하다.

### Q3. 정전이 나면?
systemd가 부팅 시 3개 유닛을 자동 기동하고, 웹 서버는 시작 시 USB를 1회 스캔한 뒤(`startup_scan`) 스케줄을 평가해 **그 시각에 맞는 예약 플레이리스트를 자동 재생**한다. 사람의 개입이 필요 없다.

### Q4. 여러 사람이 동시에 접속하면 충돌하지 않나?
- 상태는 **서버가 단일 소유**하고 SSE로 모든 클라이언트에 방송하므로, 한쪽의 조작이 모두에게 즉시 반영된다(마지막 요청이 이김).
- mpv 소켓 쓰기는 `threading.Lock`으로 직렬화된다.
- 다만 이 시스템은 **관리자 소수가 쓰는 환경**을 전제하므로, 낙관적 잠금이나 편집 충돌 병합 같은 기법은 도입하지 않았다(YAGNI).

### Q5. 파일 이름을 바꾸면 플레이리스트가 깨지나?
**깨지지 않는다.** 식별자가 경로가 아니라 내용 기반 `content_id`이기 때문이다(§3.3). 이름 변경·USB 내 폴더 이동 모두 동일한 id로 다시 인식된다.

### Q6. 보안은 어떻게 처리했나?
공용 비밀번호를 PBKDF2-HMAC-SHA256(20만 회, 임의 salt)로 해시 저장하고, 세션은 HMAC-SHA256 서명 쿠키(httponly, samesite=lax)로 관리한다. 비밀번호 비교는 상수 시간(`hmac.compare_digest`), 연속 실패 5회 시 429로 무차별 대입을 완화한다. 다만 **내부망 전용 시스템**이라는 전제이며, 외부 노출이 필요하면 HTTPS(리버스 프록시)와 사용자별 계정이 추가로 필요하다 — 현재 범위 밖이다.

### Q7. 확장한다면 무엇을 하겠는가?
- **HDMI-CEC**로 TV 전원까지 제어(예약 시작 시 TV 자동 켜기)
- 화면 분할·자막 오버레이(공지 텍스트 띄우기)
- 다중 파이 그룹 재생(여러 교실 동기화) — 현재 구조는 단일 노드 전제
- 외부 노출용 HTTPS + 사용자별 계정

### Q8. 가장 어려웠던 기술적 문제는?
세 가지를 꼽는다.
1. **재생 중 큐 편집 시 현재 항목 유지** — 인덱스로 추적하면 앞쪽이 삭제될 때 어긋난다. 블록 객체의 정체성(`is`)으로 추적해 해결했다(§3.5).
2. **사진의 진행바** — mpv가 정지 이미지의 `time-pos`를 신뢰할 수 없게 준다. 단조 시계 기반 벽시계 계산으로 대체했다(§3.8).
3. **mpv `end-file` 이벤트의 오탐** — `loadfile`로 파일을 교체할 때도 `end-file`이 발생해 "다음 곡으로 연쇄 전환"되는 버그가 있었다. 종료 사유를 검사해 자연 종료(`eof`)·오류(`error`)일 때만 진행하도록 고쳤다.
   ```python
   def _on_end(self, reason="eof"):
       if reason not in ("eof", "error"):
           return          # stop/redirect 등은 무시 → spurious advance 방지
   ```

### Q9. 테스트는 어떻게 신뢰하는가? 실제 하드웨어 없이 한 테스트인데?
- **도메인 로직**(큐·셔플·반복·예약 판정·식별자 계산)은 하드웨어와 무관한 순수 로직이므로 가짜 mpv 주입으로 충분히 검증된다.
- **하드웨어 의존 부분**(실제 재생·USB·4K·해상도)은 라즈베리파이에서 직접 확인한다는 규칙을 세웠다.
- 즉 **"순수 로직은 자동화 테스트, 하드웨어는 실기 검증"**으로 역할을 나눴다. 이 경계를 명확히 하기 위해 도메인 계층의 순수성을 규칙으로 강제했다.

### Q10. 왜 SPA(Vue)인가? 서버 렌더링 템플릿이 아니라?
재생 상태가 **초 단위로 변하고 여러 클라이언트에 동시 반영**되어야 한다. 서버 렌더링이면 상태 변화마다 페이지를 다시 받아야 하고, 드래그로 타임라인을 편집하는 상호작용(§7.2)은 클라이언트 상태 없이는 구현이 어렵다. 또한 빌드 산출물이 정적 파일이라 **FastAPI가 그대로 서빙**할 수 있어 별도 웹서버가 필요 없다.
